## 1. **引言**

### 1.1. **目的**
本文档详细描述了 Protocol Bank 平台的功能需求、用户交互和系统行为。它将作为产品、设计和开发团队之间沟通的桥梁，确保对产品功能的共同理解，并指导后续的开发和测试工作。

### 1.2. **范围**
本文档覆盖了 Protocol Bank 平台的所有核心功能，重点关注 **流式支付 (Stream Payment)** 模块，包括其仪表盘、支付网络可视化、交易历史和批量创建等功能。后台管理系统(Admin)的功能不在本文档讨论范围内。

## 3. **功能需求详解**

### 3.1. **用户认证**

- **功能描述:** 用户通过连接其非托管的加密钱包来访问平台。
- **用户流程:**
  1. 用户点击页面右上角的 “Connect Wallet” 按钮。
  2. 平台弹出支持的钱包列表 (如 MetaMask)。
  3. 用户选择钱包并授权连接。
  4. 连接成功后，按钮区域显示用户的钱包地址和余额，用户即登录成功。
  5. 用户可以随时点击 “Disconnect” 断开连接，退出登录状态。

### 3.2. **主导航与页面路由**

- **功能描述:** 平台采用顶部导航栏进行主要功能模块的切换，路由基于URL hash。
- **导航项:**
  - **Home:** 用户登录后展示核心的可视化仪表盘(默认为`FlowPaymentVisualization`)，未登录时显示产品介绍着陆页(`LandingPage`)。
  - **Payments:** 集合了所有支付功能的页面，通过内部的Tab页切换 **常规支付**、**流式支付** 和 **网络支付**。
  - **Analytics:** 统一的财务分析页面，提供深度的数据洞察和报表。
  - **Automation:** 自动化工作流构建器页面。

### 3.3. **流式支付 (Stream Payment) 模块**

这是平台的核心功能之一，位于 **Payments** 页面的 “Stream Payment” 标签页下。

#### 3.3.1. **仪表盘 (Dashboard) 界面**

- **布局:** 整个仪表盘从上到下由三部分组成：**统计卡片**、**支付网络关系图** 和 **支付交易历史列表**。
- **数据状态:**
  - **无数据/未登录状态:** 统计卡片数值显示为0，网络图显示预设的、动态的测试数据动画，交易列表显示为空状态的提示信息。
  - **有数据/登录状态:** 所有组件都将从服务器和区块链获取真实数据并渲染。

#### 3.3.2. **统计卡片 (Stats Cards)**

- **功能:** 以醒目的方式展示关于流式支付的关键性能指标(KPIs)。
- **指标项:**
  - **Total Payments:** 当前用户创建的有效支付流总数 (整数)。
  - **Total Amount:** 所有有效支付流的总金额 (格式化货币，如 `≡ 1,234.56`)。
  - **Suppliers:** 支付流所指向的唯一收款人地址总数 (整数)。
  - **Average Payment:** 总金额 / 总支付流数量 (格式化货币)。

#### 3.3.3. **支付网络关系图 (Payment Network Graph)**

- **功能:** 提供一个交互式的、力导向的图表，实时可视化用户的所有流式支付关系。
- **数据源:**
  - **未登录时:** 使用一个预定义的、包含多个节点的模拟数据集，并以动画形式展示，用于功能演示。
  - **登录后:** 通过后端API，结合从区块链(如 Etherscan API)获取的用户钱包地址相关的交易数据，动态生成关系图。
- **节点 (Nodes):**
  - **主节点 (用户):** 位于图表中心，代表当前登录用户。
  - **二级节点 (分公司):** 代表与主节点有直接关联的大型实体，如分公司或主要合作伙伴。
  - **叶节点 (供应商/客户):** 代表最终的收款方，通常数量较多，分布在图表外围。
- **颜色与状态映射:**
  - **绿色:** 支付流处于活跃状态，资金正在流动。
  - **红色:** 支付流因错误(如资金不足)而失败。
  - **灰色:** 支付流已由用户手动停止或已正常结束。
- **边与交易 (Edges & Transactions):**
  - **连接线:** 代表一个支付流关系，连接付款方和收款方。
  - **橙色粒子:** 代表在支付流上发生的单笔资金转移事件，沿连接线从付款方流向收款方，形成动画效果。
- **交互性:**
  - **平移 (Pan):** 用户可以按住并拖动图表背景来移动整个视图。
  - **缩放 (Zoom):** 用户可以通过鼠标滚轮来缩放图表。
  - **点击 (Click):** 点击任何一个节点，会弹出该节点的信息卡片，显示地址、关联的支付流总额、状态等详细信息。

#### 3.3.4. **支付交易历史列表 (Payment Transactions List)**

- **功能:** 在网络图下方，以表格形式详细列出所有的支付交易记录。
- **列定义:**
  - **DATE:** 交易发生的日期。
  - **SUPPLIER:** 收款方的名称或地址。
  - **CATEGORY:** 交易的业务类别(如市场营销、原材料采购等)。
  - **AMOUNT:** 交易金额。
  - **STATUS:** 交易状态(成功、失败、进行中)，用不同颜色的图标表示。
  - **TX HASH:** 该笔交易在区块链上的哈希值，点击后应在新标签页中打开对应的区块链浏览器页面(如 Etherscan)。
- **筛选与分类:**
  - **日期筛选:** 提供 “From” 和 “To” 两个日期选择器，用户可以选择一个时间范围来过滤交易。
  - **分类过滤:** 在列表上方提供一组分类标签按钮(如 AI Services, Marketing, Logistics等)，用户点击标签可以只显示该类别的交易。提供一个 “All” 按钮来清除分类过滤。

#### 3.3.5. **创建与管理功能**

- **创建单个支付流 (`Create Stream`):**
  - 点击 “+ Create Stream” 按钮，弹出一个模态框。
  - **表单字段:**
    - `Recipient Address`: 收款人的钱包地址 (必填，需进行地址格式验证)。
    - `Total Amount`: 支付流的总金额 (必填，数字类型)。
    - `Start Time / End Time`: 支付流的开始和结束时间 (日期选择器)。系统根据此计算出 `duration`。
    - `Currency/Token`: 选择支付的加密货币类型 (如 ETH, USDC)。
  - **提交:** 点击 “Create” 后，调用智能合约执行创建操作，并给出交易状态反馈。
- **批量创建支付流 (`Batch Create`):**
  - 在 “Create Stream” 按钮旁边，应有一个 “Batch Create” 按钮，点击后弹出 `BatchStreamModal`。
  - **CSV模板下载:** 模态框内提供一个 “Download Template” 链接，用户可以下载包含 `recipient_address`, `total_amount`, `start_time`, `end_time` 等列的CSV模板文件。
  - **CSV上传:** 用户填写完模板后，通过文件上传控件将CSV文件上传。
  - **数据预览与验证:** 上传后，系统在模态框内预览解析出的数据列表，并对每一行的数据格式进行校验，标记出错误行。
  - **提交:** 用户确认无误后，点击 “Create Streams”，后端将所有有效的支付流打包成一笔或多笔批量交易发送到智能合约，以节省Gas费。
  - **结果反馈:** 界面实时显示批量创建的进度和最终结果(成功多少，失败多少)。

## 4. **API 接口与数据模型 (高阶)**

| API 端点 | HTTP 方法 | 描述 | 数据模型 |
| :--- | :--- | :--- | :--- |
| `/api/streams` | `GET` | 获取当前用户的流式支付列表和相关统计数据。 | `Stream`, `Statistics` |
| `/api/streams` | `POST` | 创建一个新的单个流式支付。 | `Stream` |
| `/api/streams/batch` | `POST` | 通过上传CSV文件批量创建流式支付。 | `[Stream]` |
| `/api/transactions` | `GET` | 根据筛选条件获取用户的交易历史记录。 | `Transaction` |
| `/api/network` | `GET` | 获取用于渲染支付网络关系图的节点和边数据。 | `GraphData { nodes, edges }` |

## 5. **错误处理**

- **表单验证:** 所有用户输入字段都应有前端和后端的双重验证。不符合格式的输入应立即给出清晰的错误提示。
- **API请求:** 对后端的API请求失败时(如网络错误、服务器500错误)，应向用户显示一个非阻塞式的Toast通知，告知“操作失败，请稍后重试”。
- **区块链交易:** 与智能合约的交互(如创建支付流)应全程跟踪交易状态，并向用户反馈：`正在处理...`、`交易成功!`、`交易失败: [失败原因]`。
- **空状态:** 当列表(如交易历史)或图表没有数据时，应显示一个友好的空状态占位符，而不是一个空白区域，并可能包含一个引导用户进行下一步操作的按钮(如“创建您的第一个支付流”)。
