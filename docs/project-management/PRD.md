## 1. **项目概述**

### 1.1. **项目简介**

Protocol Bank 是一个基于区块链的去中心化跨境支付平台，旨在替代传统的SWIFT系统，为全球用户提供更快速、更低成本、更透明的支付解决方案。平台利用智能合约技术，支持实时流式支付、批量支付、定时支付和智能合约托管等高级功能，并通过可视化的仪表盘和分析工具，帮助企业和个人用户管理其财务活动。

### 1.2. **项目目标**

- **降低跨境支付成本:** 通过去中心化网络和净额结算引擎，将交易费用降低99%以上。
- **提高支付速度:** 实现近乎实时的全球资金流转，替代传统银行系统的多日结算周期。
- **增强透明度和安全性:** 所有交易记录在区块链上，不可篡改，并通过智能合约确保资金安全。
- **提供灵活的支付解决方案:** 满足SaaS订阅、自由职业者薪酬、供应链金融等多种商业场景的需求。
- **构建可扩展的金融生态:** 引入AI代理市场、DeFi集成等功能，打造一个开放的、可编程的金融平台。

### 1.3. **目标用户**

- **跨国企业:** 需要高效、低成本的全球资金管理和供应链支付解决方案的公司。
- **SaaS和订阅服务提供商:** 需要处理大量、高频订阅费用的企业。
- **自由职业者和远程工作者:** 需要接收来自全球雇主的即时付款的个人。
- **金融机构和开发者:** 希望在平台上构建创新金融应用和服务的合作伙伴。

## 2. **核心功能需求**

### 2.1. **支付功能**

| 功能模块 | 核心需求描述 |
| :--- | :--- |
| **常规支付** | 支持用户通过连接的加密钱包(如MetaMask)或平台托管钱包进行单次即时支付。 |
| **流式支付 (Stream Payment)** | - **实时资金流:** 支持按秒计费的连续支付流，资金实时从付款方转移到收款方。<br>- **批量创建:** 支持通过CSV文件导入，一次性创建多个支付流。<br>- **仪表盘:** 提供统计卡片(总支付额、供应商数量等)、支付网络关系图、交易历史和趋势图表。<br>- **支付网络可视化:** 实时、交互式地展示支付关系网络。 |
| **批量支付 (Batch Payment)** | - **多笔交易:** 允许用户上传CSV文件，一次性处理对多个地址的支付。<br>- **降低Gas费:** 通过智能合约优化，将多笔交易打包在一个区块链事务中，显著降低Gas成本。 |
| **定时支付 (Scheduled Payment)** | - **自动化支付:** 用户可以设置在未来的特定时间或按固定周期(每日、每周、每月)自动执行的支付。<br>- **可视化流程构建:** 提供拖放式界面，让用户可以设计复杂的、有条件的支付逻辑。 |

### 2.2. **Stream Payment 详细需求**

#### 2.2.1. **仪表盘 (Dashboard)**

- **统计卡片:**
  - **总支付额 (Total Amount):** 当前用户所有有效支付流的总金额。
  - **供应商/收款人数量 (Suppliers):** 当前用户支付流涉及的独立收款人总数。
  - **总支付流数量 (Total Payments):** 当前用户创建的有效支付流总数。
  - **平均支付额 (Average Payment):** 平均每个支付流的金额。
- **支付网络关系图 (Payment Network):**
  - **节点定义:**
    - **主节点 (中心):** 代表当前用户或其公司总部。
    - **二级节点:** 代表用户的分公司或主要业务部门。
    - **绿色叶节点:** 代表供应商、客户或最终收款人。
  - **节点状态与颜色:**
    - **绿色:** 支付流活跃且支付成功。
    - **红色:** 支付失败或被取消。
    - **灰色:** 支付流已停止或完成。
  - **连接线与交互:**
    - **橙色圆点:** 代表每一笔具体的交易，沿连接线流动。
    - **交互:** 用户可以拖动、缩放图表，点击节点查看详细信息(如收款人地址、总金额、状态)。
  - **数据来源:** 实时更新，从未登录时的测试动画数据，到登录后从用户加密钱包地址关联的Etherscan等区块链浏览器调取的真实交易数据。
- **交易历史列表 (Payment Transactions):**
  - **布局:** 位于支付网络关系图下方。
  - **内容:** 显示详细的交易列表，包括日期、供应商/收款人、类别、金额、状态和交易哈希(TX HASH)。
  - **筛选与分类:** 支持按日期范围筛选，并按预设的类别(如AI服务、市场营销、原材料等)对交易进行分类过滤。

#### 2.2.2. **创建与管理**

- **创建单个支付流:** 提供表单，用户可以输入收款人地址、总金额、支付周期(开始/结束时间)等信息来创建一个支付流。
- **批量创建支付流:**
  - **CSV导入:** 提供一个模态框(Modal)，用户可以下载CSV模板，填写收款人地址、金额等信息后上传，系统将自动为每一行记录创建一个支付流。
  - **CSV导出:** 允许用户将当前的支付流列表导出为CSV文件。

### 2.3. **其他核心功能**

| 功能模块 | 核心需求描述 |
| :--- | :--- |
| **财务分析 (Analytics)** | 提供多维度的数据分析和可视化报表，帮助用户理解其现金流、支出分布和支付趋势。 |
| **自动化 (Automation)** | 允许用户通过可视化流程构建器创建复杂的、基于事件触发的自动化金融工作流。 |
| **供应商管理 (Suppliers)** | 提供一个界面来管理供应商信息，包括联系方式、支付历史和合规性状态。 |
| **用户认证 (Authentication)** | - **钱包连接:** 支持通过MetaMask等主流钱包进行连接和登录。<br>- **后台管理:** 为银行或平台管理员提供独立的、基于用户名/密码的登录后台。 |

## 3. **非功能性需求**

| 类别 | 需求描述 |
| :--- | :--- |
| **性能** | - **API响应时间:** 核心API的P95响应时间应小于200毫秒。<br>- **页面加载速度:** 关键页面(如Dashboard)的首次内容绘制(FCP)时间应小于2秒。<br>- **并发处理:** 系统应能支持至少1000个并发用户同时在线操作。 |
| **安全性** | - **智能合约:** 所有智能合约必须经过第三方专业机构的审计。<br>- **数据传输:** 所有前后端通信必须使用HTTPS/WSS加密。<br>- **API防护:** API需具备认证授权、速率限制、防SQL注入、防XSS/CSRF等基础安全措施。 |
| **可用性** | - **响应式设计:** 平台必须在桌面和主流移动设备上提供良好的用户体验。<br>- **国际化:** 界面文本支持多语言切换(至少支持英文和中文)。<br>- **容错性:** 系统应具备优雅的错误处理和恢复机制，对用户操作提供清晰的反馈。 |
| **可扩展性** | - **模块化架构:** 前后端应采用模块化设计，便于未来独立开发和部署新功能。<br>- **多链支持:** 架构设计应考虑未来扩展到其他主流区块链网络(如Polygon, Solana等)。 |

## 4. **项目范围**

### 4.1. **范围内 (In Scope)**

- 本文档中定义的所有核心功能和非功能性需求。
- 前端用户界面、后端API和相关智能合约的开发、测试与部署。
- 在Sepolia测试网上进行完整的端到端测试。
- 将所有代码变更同步到指定的GitHub仓库。

### 4.2. **范围外 (Out of Scope)**

- 原生移动应用(iOS/Android)的开发。
- 除Sepolia和主网之外的其他区块链网络的直接集成。
- 需要与传统银行系统进行法币交易的完整解决方案。
